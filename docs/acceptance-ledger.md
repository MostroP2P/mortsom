One row per scenario and platform. A cell is **accepted** only after a live run through the real app v2 UI
proves the assertions in [spec.md](../spec.md) section 2 and finishes verified cleanup. Builds, unit tests,
onboarding, identity probes, cancellation diagnostics and skipped cases never count.

dispute families (spec section 8) is accepted on both platforms. The dispute family ran on 2026-09-10 with
the clients built from app branch `feat/mortsom-dispute-back-id` (`6222334`, the dispute screen's
`appbar.back`), each run registering its own solver with the daemon. The expiration
family ran on a stack rebuilt on 2026-09-10 for the declared `order_expiration_secs` of 600 (daemon
`6e18952f…`), with the clients built from app branch `feat/mortsom-order-expiry-define` (`d03afed`). All 2026-09-10 runs are on the Mortsom-owned stack (daemon
`f17567fc…`) with the app at `e8d7c06` (branch `feat/mortsom-range-and-rating-ids`).

went active is proven by the relay's `canceled`, then by the maker's app no longer listing it on a loaded
My Trades). App v2 drops such a trade from My Trades since `b06ad0af` instead of showing it cancelled.

platforms, with the clients built from app `main` at `f15e6bc`. Linux passed 13 of 14 and Web all 13 it ran,

## Known app v2 product issues

### Second create form of a session keeps submit disabled (open)

Twice on 2026-09-10 (`20260910T230716Z-be358da32fa8`, `20260910T233238Z-f2d39b37d22b`) the second order Alice
created in one session showed the amount, the currency, the custom payment method and the fixed price, and
the preview priced the order, while `order.create.submit` stayed disabled; typing the method and the price
again changed nothing. Leaving the form with `order.create.cancel` and filling a fresh one submits at once
(`20260910T235331Z-93b77b09d64d`, three orders in one session). The form's validity is
`hasPayment && sats && amount` over Riverpod state that the screen resets in a microtask on `initState`; the
custom-method text is visible while its provider reads empty, which points at that reset racing the
section's `TextEditingController` on a reopened screen. To be filed against `MostroP2P/app`; the adapter's
refill is a workaround, not a fix.

### Web client can die when its own pending order expires (open)

In two of three `pending_order_expires` attempts on Web (2026-09-10) Alice's Chromium died the moment her
client applied the book's `canceled` for her own pending order, with `MyOrderScreen` open; Bob's browser
was unaffected and the Linux client handles the same event fine. The third attempt, with
`MORTSOM_WEBDRIVER_VERBOSE=1` (ChromeDriver's full log kept as `driver.log`), passed and showed no crash.
Next time it happens with the verbose log on, the DevTools events around the death will say whether the
page crashed or was detached. Until then the cell is accepted on its passing run.

### Web build did not persist trades (fixed locally 2026-09-09)

Two independent causes, both fixed on the app's `feat/mortsom-linux-accessibility` branch, upstream PR
MostroP2P/app#408: the `wasm32` storage backend stubbed every trade operation (`fe7fd55` adds the `trades` and
`trade_keys` IndexedDB stores, part of app issue #233), and the Dart bootstrap skipped `init_db` on the web
altogether (`def4d40`), which also meant the "implemented" web chat store had never been opened.

### Optimistic cancel label

`cancel_order` in the app's Rust core (`rust/src/api/orders.rs`) marks the trade `Canceled` in the local
database as an optimistic update regardless of the order's status. For an `active` or `fiat-sent` order the
daemon only opens a cooperative cancel and keeps the seller's hold, so the requesting user sees "cancelled"
while their sats are still escrowed. The app's own FSM (`rust/src/mostro/fsm.rs`) already says the status
must not change on a cooperative cancel request. Mortsom no longer trusts that label; the app should apply
the FSM transition instead of a blanket `Canceled`. To be filed against `MostroP2P/app`.
